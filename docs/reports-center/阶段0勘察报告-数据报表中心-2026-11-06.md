## 一、头号结论：报表就建在生产系统上，技术栈没有悬念

**生产环境今天跑的是老 CRM**：Cloudflare Workers + D1，仓库为 **billow741/sub-crm**（api/ 为 Worker 后端，src/ 为管理端，另有 parent-portal / teacher-portal / org-portal）。线上 API 根路径返回的端点是 students / packages / classes / payments / teachers / settings / search / dashboard，2026-11-06 探活实证在跑。

sunnybridge-mvp（FastAPI + Supabase）是已弃用的重构尝试，与生产无关，报表不考虑它。**原方案的 D1/SQLite 口径成立**（strftime 聚合、无 DATE_TRUNC）；评审版预留的 PostgreSQL 分支作废。原待拍板 D1 就此消解：报表建在 sub-crm 生产系统内，按其现有 api 路由与权限模式扩展。

规模参照（2026-08-24 生产备份）：学员 16、教师 5、课程记录 212 节（2026-03-18 至 08-30）、收款 26 笔、教师结算 18 笔、机构 5 家、课时流水 95 条。此量级下原方案与评审版谈的预聚合表、5–15 分钟缓存、全表扫描优化全部不必要，任何合理的聚合查询都是毫秒级。

## 二、生产系统（老 CRM / D1）真实数据模型要点

与报表相关的表共 13 张：students、packages、classes、payments、teacher_payments、hour_changes、leads、organizations、org_packages、org_hour_allocations、org_settlements、org_settlement_items、progress_reports、assessments、textbooks / textbook_units（另有 courses 课程产品表、bill_records、notifications、ops_tasks、settings）。

关键事实（均有备份或迁移实录为据）：

1. **课时余额是学员身上的计数器**：students.total_hours / used_hours（整数）。packages 表存在但 **0 行数据**，且 classes.package_id 在 212 节课中 **100% 为 NULL**、payments.package_id 在 26 笔收款中 **100% 为 NULL**——课包从未真正启用，消课不归属任何课包。
2. **收款**：payments（amount REAL、payment_method ∈ cash/wechat/alipay/bank/other/gift、hours 本次购课时、date 日期字符串、organization_id 默认 1）。金额有 CHECK(amount >= 0)，**没有负数退款行这种表示**；退款体现在 packages.status='refunded' 与 hour_changes 的 adjust 记录。'gift' 是支付方式枚举之一，即赠送的现成标记。
3. **教师课酬**：teacher_payments 按周期结算（period_start/end、total_classes、total_hours、hourly_rate、total_amount、status pending/paid/cancelled、payment_method ∈ gcash/bank/cash/other，另有 count_50min / count_25min 字段）。真实费率只有两档：150（15 笔）与 100（3 笔）；收款侧家长课价约 ¥30–50/课时。**费率 150 若按人民币计，每节课必亏本——教师课酬实际是菲律宾比索，只是系统里从未有币种字段**；settings 表里存的 currency='CNY' 只是收款币种。这坐实了评审版的多币种担忧，且比评审版设想的更原始：不是"字段设计不规范"，是币种信息根本不存在于数据中、只存在于业务常识里。
4. **课时流水**：hour_changes（type ∈ class / payment / adjust / class_consume、amount、ref_type / ref_id、related_id）。但覆盖不全：95 条流水对 212 节课，其中 class 类仅 62 条。**消课统计必须以 classes 为准，流水只作辅助核对，不能当唯一真相源。**
5. **课堂与反馈**：classes 自带 fb_* 一组 TEXT 字段（fb_vocab / fb_patterns / fb_grammar / fb_pronunciation_errors / fb_grammar_errors / fb_teacher_message / fb_homework 等）是文本反馈；约 124/212 节课填了 fb_vocab（8 月数据）。classes 另有 is_trial 标记、textbook_code / unit_number / page_from / page_to、duration、actual_start_at / actual_end_at、organization_id。现行 schema 又新增了五维评分与录像字段，见第三节。
6. **多维评分有两套**：① classes.fb_score_* 五维（phonics / vocab / speaking / listening / engagement，迁移 031，每节课评分）；② assessments 表 10 个 INTEGER 分项（听/说/读/写/课堂各 2 项）+ 文字评语，status draft/published，是阶段/体验评估，8 月备份中仅 2 条。报表"能力成长"以 fb_score_* 为主口径，assessments 为辅。
7. **里程碑报告**：progress_reports.report_type 现行枚举为 milestone_8 / milestone_30 / milestone_60 / milestone_100 / level_up（原为 10/30/60，迁移 030 改名并新增 100 档；与原方案一致）。
8. **教材**：textbooks + textbook_units + **student_textbook_progress**（迁移 019 新增，含 current_unit / current_lesson / total_classes_done / status）。classes 上的 textbook_code 填报率低（8 月 25/212）只影响逐课推导口径，进度报表应以 student_textbook_progress 为主源（线上数据量待阶段 1 核）。
9. **机构 B 端是真实存在的**：organizations（unit_price_cny 默认 80、credit_limit_cny、settlement_day）、org_packages（total_hours、unit_price_cny、amount_cny、paid_amount_cny、status pending/partial_paid/paid）、org_settlements（amount_due_cny、status pending/paid）+ org_settlement_items（逐课明细，unit_price_cny / subtotal_cny，挂 class_id）。机构结算全程 CNY 计价，不涉及汇率。量很小（机构 5 家、结算单 2 张）。
10. **日期与时区**：业务日期是日期字符串（classes.date、payments.date），按月聚合用 strftime 没问题；created_at 是 SQLite datetime('now') 即 UTC，按创建时间跨月统计会偏 8 小时，报表应优先用业务日期字段。students.last_class_at 字段存在但只维护了 4/16 人，流失预警应以 MAX(classes.date) 现算。
11. **漏斗顶端**：leads 表存在（官网线索），仅 3 条；学员状态只有 active / inactive / graduated 三档，没有原方案设想的"潜在→学习中→暂停→结课"完整漏斗状态机。

## 三、现行 schema 相对 8 月备份的增量（以 sub-crm 仓库为准）

8 月备份之后生产系统继续演进，以下字段/表均已在现行 api/schema.sql 或 migrations 中确认存在，报表设计按此为准：

1. **课时系数（迁移 009）**：25 分钟课不按 0.5 计，按可配置系数折算课时，默认 **0.66**（settings.short_class_coefficient，机构可用 organizations.short_class_coefficient 覆盖）。完课时由 classComplete 逻辑按系数写入 classes.hours——**报表统计消课课时直接 SUM(classes.hours)，不要再按 duration 二次折算**。教师双费率：teachers.hourly_rate（50 分钟）+ hourly_rate_25（默认 80）；机构双单价：organizations.unit_price_cny（50 分钟）+ unit_price_25_cny（默认 50）；teacher_payments 已按 count_50min / count_25min × rate_50min / rate_25min 分档结算，org_settlement_items 有 duration_type。
2. **每节课五维评分（迁移 031）**：classes 新增 fb_score_phonics / fb_score_vocab / fb_score_speaking / fb_score_listening / fb_score_engagement 五个 INTEGER 分数。这正是原方案"阶段五维综合评分"的真实落点（在 classes 上、不叫 fb_score_* 的设想名之外，字段名恰好就是 fb_score_* 前缀）。031 较新，历史覆盖率待阶段 1 对线上库查非空率。
3. **录像字段（迁移 020/021）**：classes.fb_recording、fb_recording_r2_key、fb_recording_status（默认 'none'）、fb_recording_duration、fb_recording_size。录像覆盖率 = fb_recording_status 非 'none' 占比，可算。
4. **教材进度表（迁移 019）**：student_textbook_progress（student_id、textbook_code、current_unit、current_lesson、total_classes_done、status in_progress/completed/paused），且 classes.js / textbooks.js 路由在用。教材进度报表有真实数据源，数据量待阶段 1 核。
5. **里程碑改名（迁移 030）**：milestone_10 → milestone_8；现行枚举（progressReports.js 的 zod 校验）为 milestone_8 / milestone_30 / milestone_60 / milestone_100 / level_up，与原方案一致。classes 另有 milestone_type 字段（迁移 026）。
6. **其他**：classes.is_self_paid（迁移 016，区分自费/机构课，支撑直营与机构口径拆分）；hour_changes.balance_after（迁移 012，流水带余额快照）；试听课课时为 0 的表结构调整（迁移 012_trial_hours_zero，试听不扣课时）；assessments 仍在（迁移 008/017），与 classes 五维评分是两套口径：assessments 是阶段/体验评估，fb_score_* 是每节课评分。
7. 已弃用仓库 sunnybridge-mvp 中的 finance/reconciliation、hours_log 等设计不再作为依据；其"双币种不混算"的思想与评审版一致，但生产报表须在 sub-crm 内重新落地。

## 五、原方案与评审版需要修正的点（汇总，已按 sub-crm 现行代码复核）

1. packages（课包）从未真正启用且已弃用（Roger 确认）：8 月备份 0 行、classes 与 payments 的 package_id 全 NULL。凡是"按课包单价核算"的设计都要改走学员混合单价（D2）。这是原方案最实质的虚构点。
2. 消课单价与币种：系统无任何币种字段（仅 settings.currency='CNY' 指收款）；教师课酬实为 PHP（费率 150/100、gcash）——评审版的多币种警告成立且是全案第一风险，处理见 D4。
3. 里程碑、课型、教材进度表、五维评分、录像字段：原方案与现行系统一致（8/30/60/100 节；25/50 分钟为主；student_textbook_progress 存在；classes.fb_score_* 五维存在；fb_recording_status 存在），无需修正——初版勘察据 8 月旧备份曾误判为虚构，已在本版撤销。
4. 评审版的权限矩阵角色（总部运营/教务等）在 sub-crm 现有角色中不存在，按现有角色落地，不要为报表新造角色体系。
5. exchange_rates 表与"金额存最小单位"：前者第一版可降级为"报表参数 + 系统设置项"（按月手工维护一个参考汇率并留痕）；后者绝不能套用到存量 REAL 字段。
6. 时区口径：业务日期字段（classes.date / payments.date）为日期字符串，strftime 按月聚合无时区问题；created_at 为 UTC，涉及跨月边界的统计一律用业务日期字段，不用 created_at。

## 六、待 Roger 拍板的口径（6 项）

- **D1 报表建在哪套系统**：【已消解】建在生产系统 sub-crm（Workers + D1）内；sunnybridge-mvp 已弃用，不再考虑。
- **D2 消课收入单价**：无课包归属已成事实。建议口径：学员混合单价 = 该学员累计实付金额 ÷ 累计购课时（剔除 gift），消课收入 = 已完成课时 × 混合单价，全站标注"估算口径"。若要精确核算，须先改业务：启用 packages 并强制 classes 回填 package_id——那是业务改造，不建议与报表捆绑。
- **D3 赠送课时**：建议口径：gift 收款不计现金收入；赠送课时摊薄混合单价（总课时含赠送），赠送课消课确认收入但单价已被摊薄，与评审版"赠送课不产生收入"的区别只在呈现。两者选一，写进阶段 1。
- **D4 教师课酬折算**：事实认定：teacher_payments 金额为 PHP。建议：报表按月取一个月度参考汇率（手工维护、留 rate/日期/来源），教师成本（CNY）= PHP 金额 × 当月汇率；历史月份不随汇率变动重算（锁定当月值）。金额卡按评审版格式双币展示。
- **D5 退款期间归属**：建议按 hour_changes adjust 的发生日冲减当期充值与课时负债，不回溯原收款期，实现简单且与现金流直觉一致。
- **D6 试听转化定义**：建议 cohort = 首次试听课所在月，窗口 30 天内出现首笔非 gift 正课收款即算转化；leads 数据太薄（3 条），漏斗第一版从试听开始，不含线索段。

## 七、建议的第一版范围（按现实裁剪后的顺序）

1. **学习分析先行**：课时健康分布 + 流失预警名单 + 里程碑计数。字段齐全、零口径争议、直接保续费。
2. **财务随后**：收款看板（✅ 部分）+ 消课与负债（D2/D3 定后）+ 教师成本与毛利（D4 定后）+ 机构结算（✅，CNY 直算）。
3. **教学分析**：负荷排行、完课率、反馈填报率、录像覆盖率、固定教师率；课型按 25/50/60 分档，课时量用系数口径。
4. **概览页最后拼装**，只汇总前三块已定口径的数字；现金流组与损益组分开呈现，沿用新系统对账页"双币种不混算"的既有纪律。
5. 硬门（沿用评审版并具体化）：上线前选一个真实月份，用 GCash 付款记录与微信/支付宝收款记录逐项对账，课时数零容差、金额只容汇率取整误差，对不上不上线。
